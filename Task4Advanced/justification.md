# Обоснование выбора событийного подхода

## 1. Текущая ситуация: проблемы монолитной интеграции

В текущей архитектуре используется **ESB на Apache Camel** и **централизованное DWH** как ядро интеграции:

```
Клиники → Camel → DWH → Camel → Финтех
           ↑          ↓
        Мед.данные  ИИ-сервисы
```

**Поток данных:**

1. Все источники отправляют данные в центральное DWH
2. DWH хранит данные и реализует бизнес-логику (триггеры, хранимые процедуры)
3. Потребители забирают данные из DWH через Camel
4. Отчеты строятся прямыми запросами к DWH

**Ключевые проблемы текущего подхода**

| Проблема                          | Проявление в «Будущем 2.0»                             | Последствия                                               |
|-----------------------------------|--------------------------------------------------------|-----------------------------------------------------------|
| **Централизованная точка отказа** | DWH — единственный источник правды                     | При падении DWH останавливаются все процессы              |
| **Высокая связанность**           | Бизнес-логика размазана по DWH, Camel и PowerBuilder   | Изменение в одном месте ломает другие системы             |
| **Низкая производительность**     | Отчеты строятся часами (сотни терабайт)                | Time-to-market аналитики — недели                         |
| **Сложность масштабирования**     | DWH на SQL Server 2008 не масштабируется горизонтально | Невозможно подключить новые домены (фарма, производители) |
| **Пакетная обработка (batch)**    | Данные обновляются раз в сутки                         | Нет near-real-time аналитики                              |
| **Сложность изменений**           | Любое изменение требует координации всех команд        | Разработка новых фич замедлена                            |

## 2. Событийный подход: новая парадигма интеграции

В целевой событийной архитектуре (Event-Driven Architecture, EDA):

```
Домен А → Событие → Kafka → Событие → Домен Б
         (публикует)  (шина)   (подписка)
```

**Принципы:**

- Каждый домен **публикует события** о том, что произошло в его границах
- Домены **не знают**, кто подписан на их события
- Подписчики сами решают, на какие события реагировать
- Данные не хранятся централизованно — каждый домен владеет своими данными

**Сравнение подходов**

| Аспект                   | Текущий подход (Camel + DWH)      | Событийный подход (Kafka + Event Streaming)          |
|--------------------------|-----------------------------------|------------------------------------------------------|
| **Модель интеграции**    | Запрос-ответ (синхронно)          | События (асинхронно)                                 |
| **Хранение данных**      | Централизованное DWH              | Распределенное (каждый домен владеет своими данными) |
| **Бизнес-логика**        | В DWH (хранимые процедуры)        | В доменах (микросервисы)                             |
| **Масштабирование**      | Вертикальное (SQL Server)         | Горизонтальное (партиционирование Kafka)             |
| **Время отклика**        | Часы (batch)                      | Секунды/минуты (streaming)                           |
| **Связанность**          | Высокая (все зависят от DWH)      | Низкая (домены независимы)                           |
| **Устойчивость к сбоям** | Низкая (единая точка отказа)      | Высокая (репликация, геораспределение)               |
| **Стоимость изменений**  | Высокая (координация всех команд) | Низкая (локальные изменения в домене)                |

## 3. Преимущества событийного подхода

### 1 Гибкость (Flexibility)

**Проблема сегодня:** Чтобы добавить новый сервис (например, фармацевтическую компанию), нужно:

1. Изменить схему DWH
2. Модифицировать бизнес-логику в хранимых процедурах
3. Настроить новые маршруты в Camel
4. Перетестировать всю систему

**Как становится с событиями:**

Новый домен «Фарма» просто:

1. Подключается к Kafka
2. Начинает публиковать свои события (`DrugShipmentReceived`, `InventoryUpdated`)
3. Подписывается на нужные события других доменов (`PrescriptionIssued`)

**Никаких изменений** в существующих доменах не требуется.

**Бизнес-выгода:**

- Подключение нового партнера — **дни вместо месяцев**
- Возможность быстро тестировать новые бизнес-модели
- Компания может покупать и интегрировать новые стартапы без перестройки IT-ландшафта

### 2 Масштабируемость (Scalability)

**Проблема сегодня:** SQL Server 2008 не масштабируется горизонтально. При росте объема данных (сотни терабайт)
производительность падает.

**Как становится с событиями:**

- **Kafka** масштабируется горизонтально через добавление брокеров и партиций
- **Потоковая обработка** (Flink) распределяет нагрузку на кластер
- **Data Lake** (S3 + Iceberg) масштабируется практически бесконечно

**Пример:** Черная пятница в финтех-сервисе — пиковые нагрузки на платежи.

- В старой архитектуре: DWH "падает", отчеты не строятся сутками
- В новой: Kafka автоматически распределяет нагрузку, потребители читают в своем темпе

**Бизнес-выгода:**

- Нет ограничений по росту бизнеса
- Возможность выхода на новые регионы с миллионами пациентов
- Предсказуемая стоимость масштабирования (линейная)

### 3 Скорость реакции (Responsiveness)

**Проблема сегодня:**

- Данные обновляются **раз в сутки** (batch-процессы)
- Отчеты строятся **часами**
- Бизнес узнает о проблемах на следующий день

**Как становится с событиями:**

- **Near-real-time обработка** (Apache Flink) — задержки секунды/минуты
- **Потоковые витрины** (StarRocks) — данные доступны мгновенно
- **Алерты** при аномалиях — немедленное оповещение

**Примеры:**

- Обнаружение мошеннической транзакции: **было — завтра, стало — через 5 секунд**
- Загрузка врачей: дашборд обновляется в реальном времени
- Отслеживание остатков лекарств: автоматический заказ при достижении порога

**Бизнес-выгода:**

- Более быстрое принятие решений
- Снижение потерь от мошенничества
- Улучшение качества обслуживания пациентов

### 4 Слабая связанность (Low Coupling)

**Проблема сегодня:** Все системы завязаны на DWH. Если DWH меняет схему — ломается всё.

**Как становится с событиями:**

Домены общаются через события, но:

- Не знают, кто подписан
- Не ждут ответа синхронно
- Используют общую схему (Schema Registry), но версионируют её

**Пример эволюции:**

1. Домен EMR публикует `EncounterCompleted`
2. Сейчас на это событие подписан только Billing
3. Через год появляется новый домен "Quality Control"
4. Он просто подписывается на то же событие — **EMR не нужно менять**

**Бизнес-выгода:**

- Команды работают независимо
- Ускорение разработки в 2-3 раза
- Снижение риска "сломать production"

### 5 Отказоустойчивость (Resilience)

**Проблема сегодня:** DWH — единая точка отказа. При его падении:

- Операторы не видят истории пациентов
- Не выставляются счета
- Останавливаются ИИ-сервисы

**Как становится с событиями:**

- **Репликация Kafka** между дата-центрами
- **Геораспределенные кластеры** (регионы работают независимо)
- **Dead Letter Queue** — проблемные события не блокируют поток
- **Идемпотентность** — повторная обработка безопасна

**Пример сбоя:** Отказал один брокер Kafka.

- Продюсеры переключаются на другой брокер
- Потребители продолжают читать с реплик
- **Бизнес не замечает сбоя**

**Бизнес-выгода:**

- 99.99% доступности сервисов
- Соответствие требованиям регуляторов к критичным системам
- Доверие пациентов и клиентов

### 6 Аудитоспособность (Auditability)

**Проблема сегодня:**

- Сложно отследить, кто и когда менял данные
- Журналы хранятся в разных системах
- Compliance-проверки — ручной труд

**Как становится с событиями:**

- **Event Sourcing** — все изменения хранятся как последовательность событий
- Каждое событие имеет метаданные: кто, когда, откуда
- Можно воспроизвести состояние системы на любой момент времени
- **Immutable log** — события нельзя изменить или удалить

**Бизнес-выгода:**

- Прозрачность для регуляторов (ЦБ, ФОМС)
- Быстрое расследование инцидентов
- Автоматический комплаенс

### 7 Поддержка новых бизнес-моделей

**Проблема сегодня:** Монетизация ИИ-сервисов требует сложной интеграции с партнерами.

**Как становится с событиями:**

- Партнеры получают **API на событиях** (подписка на нужные топики)
- Использование ИИ-сервисов generates событие `AIServiceConsumed`
- Billing домен подписан и выставляет счета партнерам
- **Новый источник дохода без изменения core-систем**

**Пример:** Фармацевтическая компания платит за доступ к обезличенным данным о назначениях лекарств.

- Публикуется событие `PrescriptionIssued`
- Партнер подписывается (с ограничениями доступа)
- Биллинг автоматически выставляет счет по количеству событий

**Бизнес-выгода:**

- Новые потоки дохода
- Монетизация данных без дополнительных затрат на разработку
- Быстрый вывод на рынок новых продуктов

### 8 Соответствие Data Mesh принципам

**Проблема сегодня:** Data Mesh (целевая архитектура) требует федеративного управления данными, но текущая архитектура
централизована.

**Как становится с событиями:**

Событийная архитектура идеально соответствует Data Mesh:

| Принцип Data Mesh           | Реализация через события                                           |
|-----------------------------|--------------------------------------------------------------------|
| **Домены владеют данными**  | Каждый домен публикует свои события, данные не покидают домен      |
| **Данные как продукт**      | События — это продукт домена с документированным SLA               |
| **Самообслуживание**        | Платформа данных предоставляет самообслуживаемый доступ к событиям |
| **Федеративное управление** | Schema Registry и Data Catalog обеспечивают единые стандарты       |

**Бизнес-выгода:**

- Масштабирование аналитики без централизованной команды
- Владельцы доменов отвечают за качество своих данных
- Быстрое подключение новых источников

## 4. Сравнительная таблица: Camel/DWH vs Event-Driven

| Метрика                                        | Camel + DWH     | Event-Driven               | Улучшение           |
|------------------------------------------------|-----------------|----------------------------|---------------------|
| **Время подключения нового домена**            | 3-6 месяцев     | 2-4 недели                 | **6-12x быстрее**   |
| **Время построения сложного отчета**           | Часы            | Секунды/минуты             | **50-100x быстрее** |
| **Задержка данных для аналитики**              | 24 часа (batch) | 1-5 минут (near-real-time) | **300x быстрее**    |
| **Количество затронутых систем при изменении** | 5-10            | 1 (только домен-источник)  | **5-10x меньше**    |
| **Доступность критичных сервисов**             | 99.5%           | 99.99%                     | **0.49% больше**    |
| **Стоимость масштабирования**                  | Суперлинейная   | Линейная                   | **Предсказуемо**    |
| **Время восстановления после сбоя**            | Часы            | Минуты                     | **10-20x быстрее**  |
